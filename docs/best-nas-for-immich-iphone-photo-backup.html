Immich's iPhone rules

  • Background: turn on Background App Refresh for Immich; iOS decides when the task runs and the app cannot force it, so open Immich from time to time; the first big upload is best done in the foreground. Immich 3.0 moved sync and upload to run in parallel inside iOS's short background window, and later 3.x releases list more iOS fixes.
  • Wi-Fi: upload is Wi-Fi only by default; the charging-only option is documented for Android.
  • iCloud: with "Optimize iPhone Storage" on, Immich downloads each original to its cache, hashes and uploads it, then clears it, which costs data and space; Immich's "Free Up Space" deletes from iCloud too (30 days in Recently Deleted), so keep iCloud as a second copy or treat the NAS as the only one knowingly.
  • Albums and formats: album sync is phone to server only, duplicates are skipped by checksum, Live Photos upload with their video (since 1.36, manual link/unlink since 1.115), RAW files are viewable.

Server and machine learning

Immich wants 6 GB minimum and 8 GB recommended, 2 cores minimum and 4 recommended, an x86-64-v2 CPU for the ML container since version 3 (the N100 qualifies), and its Postgres database on local SSD, never a network share; thumbnails and transcodes add 10–20% to the library. Machine learning can be disabled or run on another machine. The one N100 owner report (a DXP4800 Plus, 43,000 photos) saw about 300 photos an hour with ML on against 5,000 with ML off, so expect days for a big first import unless ML waits. Video transcoding can use Quick Sync (experimental; encoding only by default) through the QSV compose extension and /dev/dri.

Remote access

Immich's guide offers three routes: a VPN such as WireGuard (needs a forwarded port), Tailscale (works behind carrier NAT with the app on phone and NAS, no open port), or a domain with HTTPS through a reverse proxy, which the mobile app reaches without a VPN; it warns never to expose port 2283 directly.
